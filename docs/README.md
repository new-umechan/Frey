# docs

基本方針:

- `docs/` は浅く保つ
- `README.md` は入口、詳細は `docs/` に置く
- 提案、判断、実装仕様、外部調査、内部検証ログを混在させない

## 文書カテゴリ

### `concepts/`

背景説明、全体像、設計思想を置く。

- 何を目指しているか
- なぜその構成なのか
- どういう責務分担か

読むための文書であり、API や型定義の正本はここに置かない。

### `research/`

外部文献、既存手法、概念調査を置く。

- まだ採用判断していない材料
- 外部資料の要約
- 調査ノート

実験 run の `vxx` ログはここに置かない。

### `reference/`

API、データ構造、モジュール仕様などの正本を置く。

- 正確に確認したい項目
- 実装と対応づける項目
- 公開インターフェースや内部構造の定義

reference は実装と一致している必要がある。
変更履歴や試行錯誤ログは置かず、正本として使えることを優先する。

### `proposal/`

これから変える設計案を置く。

- 実装前に詰めたい仕様案
- 採用前のモジュール設計
- 大きな再設計案
- 未来向きの意図、スコープ、成功条件

形式の詳細は`docs/proposal/template.md`を参考にする。
ここにある文書は正本ではない。採用後は `decisions/` と `reference/` へ反映する。

各 proposal の先頭には次を明記する。

- `Status`
- 必要なら `Reason`
- 必要なら `Replaced by`

`Status` は次を使う。

- `Draft`
- `Accepted`
- `Rejected`
- `Superseded`

不採用になった proposal は原則として削除しない。
`Status: Rejected` または `Status: Superseded` を付け、必要なら短い理由を残す。

### `operations/`

現在有効な開発・テスト手順を置く。

- 日常開発
- 検証手順
- 現在の運用フロー

将来計画、設計議論、比較履歴はここに置かない。

### `operations/bench/`

ベンチマークの実行方法、artifact の読み方、内部検証ログを置く。

- ベンチマークの実行方法
- artifact の読み方
- 比較履歴
- 棄却した仮説
- `vxx` 系の検証ログ

実装仕様の正本はここに置かない。

## Decision Record

採用済みの重要判断は、必要に応じて `docs/decisions/` に短く残す。

残す対象:

- 後戻りコストが高い判断
- 将来また理由を確認したくなる判断
- 将来の参照価値が高い判断

残さない対象:

- 小さな命名変更
- 一時的な試行錯誤
- 単なる思考ログ

1文書1判断を原則とする。
