# docs

基本方針:

- `docs/` は浅く保つ
- `README.md` は入口、詳細は `docs/` に置く
- 採用済み仕様の正本と、未採用の案を分ける

## 文書カテゴリ

### `concepts/`

背景説明、全体像、設計思想を置く。

- 何を目指しているか
- なぜその構成なのか
- どういう責務分担か

読むための文書であり、API や型定義の正本はここに置かない。

### `reference/`

API、データ構造、モジュール仕様などの正本を置く。

- 正確に確認したい項目
- 実装と対応づける項目
- 公開インターフェースや内部構造の定義

reference は実装と一致している必要がある。
理由説明はにとどめ、正本として使えることを優先する。

### `proposal/`

未実装、未確定、再設計中の案を置く。

- 実装前に詰めたい仕様案
- 採用前のモジュール設計
- 大きな再設計案

形式の詳細は`docs/proposal/template.md`を参考にする。
ここにある文書は正本ではない。採用後に `reference/` へ反映する。

各 proposal の先頭には次を明記する。

- `Status`
- 必要なら `Reason`
- 必要なら `Replaced by`

`Status` は次を使う。

- `Draft`
- `Accepted`
- `Rejected`
- `Superseded`

不採用になった proposal は原則として削除しない。
`Status: Rejected` または `Status: Superseded` を付け、必要なら短い理由を残す。

### `operations/`

開発、テスト、ベンチ運用などの手順を置く。

- 日常開発
- 検証手順
- 重いベンチやデータ準備

`bench/` は件数が多いため、`operations/` 配下で独立させる。

### `research/`

調査途中のメモ、文献比較、探索ログを置く。

- 未確定の仮説
- 外部資料の要約
- 比較検討の途中経過

採用済み仕様の正本はここに置かない。

## Decision Record

採用済みの重要判断は、必要に応じて `docs/decisions/` に短く残す。

残す対象:

- 後戻りコストが高い判断
- 将来また理由を確認したくなる判断
- 将来の参照価値が高い判断

残さない対象:

- 小さな命名変更
- 一時的な試行錯誤
- 単なる思考ログ

1文書1判断を原則とする。
