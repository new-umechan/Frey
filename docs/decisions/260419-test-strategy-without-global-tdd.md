# テスト戦略: 全体方針としてTDDは採用しない

## Status

Accepted

## Context

Frey は Docs-first を前提に、仕様の正本を `docs/reference/`、重要判断と検討状態を `docs/decisions/` で管理している。
設計の主眼は、実装前に責務境界、公開 state、運用手順、近似の前提を文書として固定することにある。

一方で本プロジェクトは、科学シミュレーションとして次の性質を持つ。

- 近似モデルとパラメータ調整を含む
- 正しさが単一の期待値一致ではなく、妥当な傾向や許容差分で評価される
- seed 固定回帰、API 契約、性能ゲートの価値が高い
- モジュールによっては文献比較とベンチ結果を見ながら仕様を詰める必要がある

このため、古典的な TDD を全体開発方針として導入するべきかを検討した。

## Decision

全体方針として TDD は採用しない。

代わりに、品質戦略は次の組み合わせで運用する。

- Docs-first による仕様先行
- Rust ユニットテストによる局所ロジック検証
- WASM API 契約テストによる外部インターフェース固定
- seed 固定回帰テストによるシミュレーション変化監視
- perf gate による性能劣化検知
- lint と format による静的品質担保

ただし、次の範囲ではテスト先行を許容する。

- 純粋関数
- 正規化や境界条件の判定
- state 遷移
- CLI 引数処理
- API 契約の追加・変更

## Rationale

TDD を全体方針として採用しない理由は次のとおり。

- シミュレーション全体の挙動は emergent であり、実装前に厳密な期待値を固定しづらい
- パラメータ調整や近似改善のたびに、実装詳細へ結びついたテストの保守コストが増えやすい
- Frey では「何を作るか」を Docs-first がすでに先行して固定している
- 既存の seed 回帰と perf gate のほうが、全体挙動の監視として実用価値が高い
- 科学モデルでは、文献整合性、統計的妥当性、計算コストの trade-off 記録が重要であり、古典的 TDD の適用範囲は限定される

## Consequences

利点:

- 実装探索とモデル調整の自由度を維持できる
- テストを実装詳細に過剰固定しにくい
- 既存の Docs-first 運用と整合する
- 回帰監視と性能監視に開発資源を集中できる

コスト:

- 実装初期の局所不具合を、TDD より遅れて検出する場合がある
- 受け入れ条件を文書に明記しないと、仕様とテストの対応が弱くなる
- 開発者が局所的にテスト先行を使うべき箇所を判断する必要がある
